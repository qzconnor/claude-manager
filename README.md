# Claude Manager

Desktop-App für Windows 11 und Linux, die mehrere Claude-Code-Instanzen nebeneinander verwaltet: Terminals in Tabs, mehrere Accounts gleichzeitig, eine durchsuchbare Session-Liste (wie `/resume`, gruppiert nach Account), ein Usage-Dashboard und eine lokale API für andere Programme.

## Funktionen

- **Terminals**: xterm.js (WebGL) mit ConPTY bzw. einem Pseudo-Terminal unter Linux. Farben, Emoji inkl. ZWJ-Sequenzen, Box-Drawing und Nerd-Font-Icons werden korrekt dargestellt. Tabs bleiben beim Seitenwechsel erhalten und lassen sich per Drag & Drop umsortieren, oben in der Titelleiste wie in der Seitenleiste. Ein Tab zeigt den Titel der Session wie in `/resume`, solange sie noch keinen hat, ihren Ordner; den Account zeigen die Farbe seines Punkts und die Infokarte. Per Doppelklick, Kontextmenü oder den Stift in seiner Infokarte bekommt er einen eigenen Namen, die Infokarte zeigt dann weiter den Titel, den Claude vergeben hat (leer lassen stellt ihn wieder her). Der Name gilt für die Session des Tabs und nach `/clear` für die neue; eine mit `/resume` geöffnete Session behält ihren eigenen Namen oder Titel. Wird es eng, werden sie schmaler wie im Browser. Ein Tab lässt sich teilen, vertikal (Alt+Umschalt+Plus) oder horizontal (Alt+Umschalt+Minus), über die beiden Buttons rechts in der Titelleiste, sein Kontextmenü oder die Befehlspalette: Das neue Terminal startet daneben bzw. darunter wie das gewählte, als Session mit demselben Account im selben Ordner oder als Shell. Teile lassen sich weiter teilen (bis zu 16 Ebenen tief, danach öffnet das neue Terminal als eigener Tab daneben), die Trennlinie ziehen (Doppelklick teilt wieder halb und halb), mit Alt+Pfeil wechselt man zwischen ihnen, die übrigen treten abgedunkelt zurück. Ein geteilter Tab zeigt seine Terminals einzeln, oben nebeneinander und in der Seitenleiste untereinander, jedes mit eigenem Status und eigenem X; ein Klick wählt es, Mittelklick schließt es, Doppelklick benennt es um, das Kontextmenü wirkt auf das Terminal unter der Maus. Strg+Umschalt+W schließt das gewählte Terminal, „Tab schließen“ im Kontextmenü (oder Mittelklick auf einen ungeteilten Tab) den ganzen Tab; über das Kontextmenü kommt ein Terminal wieder in einen eigenen Tab. *Maximieren* im Kontextmenü (oder *Teil maximieren* in der Befehlspalette) zeigt einen Teil allein über den ganzen Tab, bis man *Alle Teile zeigen* wählt oder ein anderer Teil die Tastatur bekommt; die anderen laufen dabei weiter. Das gibt es mit den Tabs in der Titelleiste und in der Seitenleiste, in Gruppen teilt man stattdessen die Gruppen. Die Aufteilung übersteht ein Neuladen des Fensters und wird mit den Tabs wiederhergestellt. Der Pfeil neben dem Plus (in der Seitenleiste neben *Neue Session*) zeigt die zuletzt genutzten Ordner aus offenen Tabs und gespeicherten Sessions: Ein Klick startet dort eine Session mit dem Account für neue Sessions, das Untermenü eine mit einem anderen Account oder eine Shell. Dieselben Ordner stehen in der Befehlspalette und auf der leeren Terminal-Seite. Unter *Zuletzt geschlossen* stehen dort auch die letzten zehn geschlossenen Sessions und Shells: Ein Klick öffnet sie wieder im selben Ordner, mit ihrem Account, ihren Startoptionen und einem eigenen Namen, eine Session macht mit ihrem Verlauf weiter. *Geschlossenen Tab wieder öffnen* in der Befehlspalette holt den zuletzt geschlossenen zurück. Die Liste gilt, bis die App beendet wird. Suche, Zoom, Kopieren/Einfügen, Umschalt+Enter für Zeilenumbrüche in Claude Code. Adressen im Terminal öffnet ein Klick; Links, die ein Programm selbst setzt (OSC 8), zeigen unter der Maus, wohin sie führen, und steht dort etwas anderes als ihre Adresse, öffnet sie erst Strg+Klick. Text mit Zeilenumbrüchen kommt in eine Shell, die jede Zeile sofort ausführen würde, erst nach Rückfrage, mit Vorschau (wie in Windows Terminal, abschaltbar unter Einstellungen › Terminal › Verhalten); Claude Code bekommt ihn ohne Frage. Dateien lassen sich ins Terminal ziehen: Wie in Windows Terminal wird ihr Pfad eingefügt, Bilder hängt Claude Code dann an. In einer Shell steht ein Pfad mit Leer- oder Sonderzeichen in einfachen Anführungszeichen, damit sie nichts darin ausführt (`$(…)`, Backticks, `;`), auch wenn der Dateibaum ihn einfügt. Beendest du Claude mit Strg+C oder `/exit` (bzw. die Shell mit `exit`), schließt sich der Tab. Bei einem Fehler bleibt er offen, einstellbar unter Einstellungen › Claude Code. Auf Wunsch merkt sich die App die offenen Tabs und öffnet sie beim nächsten Start in derselben Reihenfolge wieder, Claude-Sessions werden dabei fortgesetzt (Einstellungen › Claude Code › Tabs beim Start wiederherstellen). Das gilt auch, wenn Windows (oder Linux) herunterfährt oder abmeldet, während die App läuft. Geht ein Tab dabei nicht auf (Netzlaufwerk nicht erreichbar, Claude Code aktualisiert sich gerade), sagt die App warum und bietet *Erneut versuchen* an; sonst versucht sie es bei den nächsten zwei Starts wieder. *Neu starten* im Kontextmenü eines Tabs beendet erst den Prozess (läuft er noch, fragt die App vorher) und startet den Tab dann an derselben Stelle neu; eine Session macht dabei mit dem Verlauf weiter, den sie gerade hat, auch nach `/resume` oder `/clear`.
- **Dateibaum**: Neben jedem Terminal lässt sich der Ordner, in dem der Tab arbeitet, als Baum aufklappen, ähnlich dem Explorer von VS Code (Knopf mit dem Dateisymbol oder Strg+Umschalt+E). Der Baum schiebt das Terminal zur Seite, statt es zu verdecken, und gehört zum Tab: Jede Session zeigt ihr eigenes Projekt, ein Browser das seiner Session, eine Session in einem Worktree dessen Ordner. Welche Bäume offen sind, übersteht einen Neustart; aufgeklappte Ordner merkt sich die App pro Projekt. In Gruppen hat jede Gruppe ihren Knopf in der Tab-Leiste und ihren Baum, oben und in der Seitenleiste sitzt er in der Titelleiste. Unter Einstellungen › Darstellung › Dateibaum steht, ob er links öffnet (Knopf vor den Tabs) oder rechts (Knopf hinter dem Menü bzw. ganz rechts in der Titelleiste); seine Breite lässt sich am Rand ziehen, ein Doppelklick setzt sie zurück. Der Baum zeigt den Git-Status wie VS Code (geändert, neu, gelöscht, umbenannt, Konflikt, Ordner mit Änderungen bekommen einen Punkt) samt hinzugefügten und entfernten Zeilen, darüber Branch, Commits vor und hinter dem Upstream und die Zahl der Änderungen; von Git ignorierte Dateien erscheinen blass oder auf Wunsch gar nicht. Der Filter-Knopf rechts neben der Zahl der Änderungen klappt die Filter des Baums auf: *Änderungen* zeigt nur die Dateien, die Git geändert sieht, *Aktivität* nur die, die Claude in der Session des Tabs gelesen, durchsucht, geschrieben oder committet hat (das Symbol dazu steht auch hier nur kurz nach dem Zugriff da); beide zusammen zeigen die Dateien von beiden. Darunter lassen sich einzelne Arten ausblenden (etwa nur Geschriebenes statt auch Gelesenes, oder nur neue Dateien), und ein Schalter blendet ignorierte Dateien aus. Ein Punkt auf dem Knopf zeigt, dass ein Filter gilt; die Filter gelten für alle Bäume und überstehen einen Neustart, die Aktivität einer Session gilt, solange die App läuft, auch über einen Account-Wechsel oder Neustart der Session. Wie beim Plugin claude-code-filetree leuchtet jede Datei auf, die Claude gerade anfasst: lila beim Lesen, blau beim Suchen (Grep und Glob, samt dem, was sie finden), orange beim Schreiben, grün für die Dateien eines Commits. Shell-Befehle zählen mit: Was Bash oder PowerShell liest oder durchsucht (`cat`, `head`, `sed`, `grep`, `Get-Content` …), erkennt die App am Befehl, und jede Datei, die sich ändert, während ein Befehl oder Skript läuft, gilt als geschrieben. Ausgenommen ist, was Git ignoriert (Build-Ausgaben, Logs), und was gerade das Schreib-Werkzeug einer anderen Session schreibt; laufen Befehle zweier Sessions im selben Ordner, zählt eine Änderung für keine. Ist der Baum dabei zu, findet die App die geschriebenen Dateien am Ende des Befehls über Git. Ihre Zeile färbt sich, ein Lichtstreifen läuft darüber; ein Symbol (Auge, Lupe, Stift, Commit) zeigt fünf Sekunden lang, was Claude tut, und der Name schimmert. Ist der Baum zu, schimmert stattdessen sein Knopf in der Farbe. Der Baum klappt dafür die Ordner auf, scrollt zur Datei, solange man nicht selbst im Baum unterwegs ist, und klappt die Ordner nach zehn Sekunden Ruhe wieder zu; ein zugeklappter Ordner pulsiert in der Farbe. Ein Klick auf eine Datei zeigt ihre Änderungen seit dem letzten Commit (`git diff HEAD`, vorgemerkte und nicht vorgemerkte zusammen) mit Zeilennummern beider Seiten, auf Wunsch die ganze Datei; eine neue Datei erscheint ganz als hinzugefügt (auch in einem Repository noch ohne Commit), eine unveränderte so, wie sie ist. Eine mit `git mv` verschobene Datei wird mit ihrem alten Stand verglichen; ist sie nur umbenannt oder nur ausführbar gemacht (`chmod`), zeigt die Ansicht sie so, wie sie ist, und sagt das. Dateien in UTF-16 (wie `>` in Windows PowerShell 5.1 schreibt) und in Latin-1 bzw. Windows-1252 erscheinen als Text mit ihren Umlauten. Haben Zeilen nur ihr Zeilenende gewechselt (CRLF ↔ LF), stehen ␍␊ bzw. ␊ an ihrem Ende, und der Kopf sagt, wie viele es sind. Bilder (PNG, JPEG, GIF, WebP, AVIF, BMP, ICO bis 8 MB) erscheinen als Bild auf einem Schachbrett, geändert vorher und jetzt nebeneinander, mit Größe in Pixeln und Bytes. Wurde eine Zeile nur zum Teil geändert, sind die geänderten Wörter in der entfernten und der neuen Zeile kräftiger hinterlegt. Ein Knopf oben stellt vorher und nachher nebeneinander, die alte Datei links und die neue rechts; lange Zeilen brechen dabei um, wo nur Zeilen dazukamen oder wegfielen, ist die andere Seite schraffiert. Die Wahl bleibt gespeichert. Der Code ist in den Farben des Terminal-Themes hervorgehoben (highlight.js, die Sprache lädt beim ersten Mal nach) und liegt auf dem Hintergrund der Terminals, durchsichtig wie sie. Die Ansicht folgt der Datei live, auch wenn Claude sie gerade schreibt oder Git sie vormerkt. Oben in der Ansicht merkt *+* die Datei vor (`git add`), *−* nimmt sie wieder heraus, der Pfeil verwirft ihre Änderungen. Jeder Abschnitt hat dazu eigene Knöpfe *Vormerken* und *Verwerfen*, Datei für Datei steht das auch im Kontextmenü des Baums. Verwerfen fragt immer erst, und die Datei, wie sie war, kommt zur Sicherheit in den Papierkorb. Eine Datei, die Git noch in keinem Commit hat, kommt ganz dorthin, eine mit `git mv` verschobene an ihren alten Platz zurück. Abschnitte gehen nur bei Dateien in UTF-8 und nur, solange die Datei so ist, wie die Ansicht sie zeigt. Oben und in der Seitenleiste teilt sie den Tab: Sie sitzt zwischen Baum und Terminal, der Trenner lässt sich ziehen. In Gruppen öffnet sie als Tab der Gruppe, kursiv als Vorschau, die der nächste Klick ersetzt; Doppelklick oder Enter behält ihn, der Baum bleibt daneben. Der Knopf zwischen der Zahl der Änderungen und dem Filter zeigt *Alle Änderungen* untereinander zum Durchscrollen, wie ein Pull Request zum Review: jede Datei als Karte in der Reihenfolge des Baums, ihr Kopf bleibt oben stehen, solange ihre Zeilen vorbeiziehen. *Gesehen* hakt eine Datei ab und klappt sie zu, der Pfeil oben springt zur nächsten ungesehenen; ändert sich eine abgehakte Datei danach, ist sie wieder offen und als *Geändert, seit gesehen* markiert. Lange Zeilen brechen um, ein Knopf oben schaltet das ab, dann scrollt die Ansicht seitwärts; die Wahl bleibt gespeichert. Auch diese Ansicht folgt dem Ordner live, und was abgehakt ist, gilt, solange die App läuft. `/diff` in einer Claude-Session öffnet sie ebenfalls, statt Claude Codes Diff-Panel, mit Tabs in Gruppen in der Gruppe rechts der Session (in einer neuen, wenn dort keine ist) und ohne eigenen Baum, denn der steht schon neben der Session (der Baum-Knopf der Gruppe blendet ihn dort ein): Die App fängt das Enter ab und leert die Eingabe, in der Session erscheint nichts, Claude sieht den Befehl nicht, es fallen keine Tokens an (Einstellungen › Werkzeuge › Claude Manager › */diff zeigt alle Änderungen*, standardmäßig an). Änderungen auf der Platte erscheinen sofort. Tippen sucht im ganzen Projekt (Git-Dateien ohne Ignoriertes), die Pfeiltasten bewegen sich wie im Explorer. Der Knopf rechts im Suchfeld sucht stattdessen im Inhalt der Dateien (`git grep`, auch außerhalb eines Repositorys, ohne Ignoriertes und Binärdateien, Groß- und Kleinschreibung egal, bis 1000 Zeilen). Die Treffer stehen nach Datei, ein Klick (oder Enter) zeigt die Zeile in der ganzen Datei und hebt sie kurz hervor. Ziehen ins Terminal fügt den Pfad ein. Das Kontextmenü erwähnt Datei oder Ordner in Claude (`@pfad`), öffnet eine Datei mit ihrem Standardprogramm (ein Programm oder Skript wie `.bat`, `.js` oder `.vbs`, das Windows dabei ausführen würde, erst nach Rückfrage), kopiert den Pfad (auch relativ), zeigt sie im Explorer und startet eine Session oder Shell in einem Ordner. Es legt auch neue Dateien und Ordner an (wie das Menü *…* oben im Baum, mit „/“ im Namen gleich samt Ordnern darin), benennt um (F2) und verschiebt nach Rückfrage in den Papierkorb (Entf). Die Menütaste oder Umschalt+F10 öffnet das Menü des gewählten Eintrags. Dabei überschreibt die App nie etwas, das es schon gibt, und bleibt im Ordner des Baums. Namen, die Windows nicht erlaubt, und `.git` nimmt sie nicht an.
- **Accounts**: beliebig viele Accounts parallel, auch mehrere Tabs mit demselben Account. Ist ein Account am Limit, läuft die Session mit einem anderen weiter, auf Wunsch automatisch (siehe unten). Accounts aus cswap lassen sich übernehmen.
- **Browser**: Eine Webseite lässt sich als eigener Tab öffnen oder als Teil eines geteilten Tabs, etwa neben der Session, die an einer Web-App arbeitet: *Browser öffnen* im Menü neben dem Plus und in der Befehlspalette, *Browser daneben öffnen* im Kontextmenü eines Tabs. Die Adressleiste nimmt Adressen (ohne `https://`, `localhost` und IP-Adressen mit `http://`) und Suchbegriffe, dazu gibt es Zurück, Vor, Neu laden und *Im Standardbrowser öffnen*. Der Tab trägt Titel und Symbol der Seite (auch in der Tab-Suche und der Befehlspalette). Links, die einen eigenen Tab wollen (`target=_blank`, Mittelklick, Strg+Klick), öffnen einen neuen Browser-Tab neben dem der Seite, mit Mittelklick und Strg+Klick im Hintergrund wie in Chrome; solange Claude in der Seite arbeitet, bleiben sie in ihr, damit Claude dort weitermachen kann. Das Kontextmenü der Seite kopiert und öffnet Links (auch in einem neuen Tab oder im Standardbrowser), lädt ohne Cache neu und öffnet mit *Untersuchen* die Entwicklertools. Strg+L springt in die Adressleiste, F5 lädt neu, Strg+Umschalt+R ohne Cache, F12 öffnet die Entwicklertools, Alt+Links/Rechts blättern zurück und vor, Strg+Plus/Minus/0 zoomen die Seite; die übrigen Kürzel der App wie Strg+Tab wirken auch, während die Seite die Tastatur hat. Stürzt eine Seite ab, sagt der Tab das und lädt sie auf Knopfdruck neu. Öffnet eine Seite Tabs oder Popups in einer Schleife, kommen nach acht in zehn Sekunden (bzw. vier offenen Popups) keine weiteren; zeigt sie einen Dialog nach dem anderen (`alert` …), lässt sich das wie in Chrome abstellen. Downloads landen wie in Chrome ohne Rückfrage im Download-Ordner, mit Windows' Markierung als Datei aus dem Internet; der Knopf rechts in der Adressleiste listet sie. Programme, Installer und Skripte führt *Öffnen* erst nach Rückfrage aus, und eine Seite, die mehr als 20 Downloads in einer Minute startet, wird für den Rest gebremst. Browser-Tabs werden mit den anderen Tabs wiederhergestellt, ihre Seiten laden erst, wenn man sie ansieht oder Claude sie braucht. Wird eine Session geschlossen, gehen die Browser neben ihr mit; nach einem Neustart oder Account-Wechsel bleiben sie bei der neuen Session. Die Seiten laufen in einem eigenen Profil, Cookies und Logins bleiben dort über Neustarts erhalten (siehe *Sicherheit*). *Browserdaten löschen* unter Einstellungen › Werkzeuge › Browser meldet überall ab und leert Cookies, die gespeicherten Daten der Seiten und den Cache, offene Seiten laden danach neu.
- **Browser für Claude**: Sessions, die die App startet, bedienen den Browser der App ähnlich wie mit Playwright: Seiten öffnen, vor und zurück, die Seite als Baum ihrer Bedienelemente lesen, klicken, tippen, Tasten drücken, in Auswahllisten wählen, scrollen, auf Text warten, die Seite auf eine Größe stellen (auch als Handy oder Tablet mit Touch und mobilem User-Agent), Screenshots (sichtbarer Teil, ein Element oder die ganze Seite), Konsole und Anfragen lesen (eine Anfrage auch mit Headern und Bodies, Cookies und `Authorization` ohne Werte), JavaScript ausführen, Dateien hochladen (aus dem Ordner der Session oder dem Temp-Ordner, nie Schlüssel oder Zugangsdaten wie `.env` oder `id_rsa`; andere Dateien lädst du selbst hoch), Dialoge (`alert`, `confirm`, `prompt`) beantworten, Elemente ziehen, Formulare in einem Schritt ausfüllen, die Seite als PDF speichern und zwischen Browser-Tabs wechseln (Claude sieht dabei seine eigenen und deine, nicht die anderer Sessions). Zum Testen kann Claude die Seite etwas vorspielen lassen: dunkles oder helles Theme, weniger Bewegung, langsames oder kein Netz (Chromes Profile 3G/4G), eine bis zu 20-fach langsamere CPU, eine andere Sprache oder Zeitzone; über der Seite steht dann, was gilt, mit einem X, das alles beendet (ebenso das Ende der Session). Es misst Ladezeit und Core Web Vitals (LCP, CLS, INP, Total Blocking Time) samt langsamsten und größten Anfragen und löscht auf Wunsch Cookies und gespeicherte Daten der aktuellen Seite, damit sie wie für neue Besucher startet. Nach einer Aktion bekommt Claude nur, was sich auf der Seite geändert hat, als Diff gegenüber dem letzten Stand; das spart bei großen Seiten viel Kontext. Inhalte fremder Seiten in iframes (Zahlungsformulare, Captchas, eingebettete Logins) liest und bedient Claude wie den Rest der Seite. Einrichten muss man dafür nichts, die App gibt jeder Session ihren MCP-Server mit. Claude nimmt den Browser im selben Tab; gibt es keinen, öffnet es einen daneben. Was Claude tut, sieht man in der Seite: Das Element, das es gerade anfasst, wird umrahmt, ein Mauszeiger mit der Beschreibung des Schritts gleitet von Klick zu Klick, und wo er klickt, zieht ein Ring auf. Unten über der Seite schwebt eine Statuspille mit dem aktuellen Schritt (ein Lichtstreifen läuft darüber, solange Claude arbeitet), der Session und *Übernehmen*; ruht Claude eine Minute, schrumpft sie auf ihr Symbol und wächst unter der Maus wieder. Das Protokoll (Knopf rechts neben der Adressleiste oder ein Klick auf den Schritt in der Statuspille) schwebt über der Ecke der Seite, bis man es schließt, und zeigt jeden Schritt mit Uhrzeit, Dauer und Ergebnis, Screenshots als Vorschaubild, dazu Fehler aus der Konsole und fehlgeschlagene Anfragen der Seite; Passwörter stehen dort nur als ••••. Gibt es neue Fehler, solange es zu ist, trägt der Knopf einen roten Punkt. Mit *Übernehmen* bedienst du die Seite selbst, Claude wartet, bis du sie mit *Zurückgeben* wieder freigibst (höchstens 10 Minuten), und liest sie dann neu ein. Stellt Claude eine eigene Größe ein, steht die Seite als Rahmen auf einer gepunkteten Fläche, darüber Größe, *Mobil* und Maßstab. Ist sie größer als ihr Platz, zeigt die App sie verkleinert; Claude sieht und bedient sie trotzdem in voller Größe, und auch deine Klicks landen an der richtigen Stelle. Das X daneben stellt die Originalgröße wieder her, ebenso das Ende der Session. Tippt Claude, hat die Seite die Tastatur nur für diesen Moment, danach geht sie dorthin zurück, wo sie war. Ein Browser in einem anderen Tab arbeitet weiter, ohne dass sein Tab nach vorn kommt; in Gruppen auch, während der Browser-Tab eine andere Session zeigt. Logins im Browser gelten auch für Claude: Alle Sessions teilen sein Profil. Ist bei einem Account Claude in Chrome an (`/chrome` › *Enabled by default* oder `CLAUDE_CODE_ENABLE_CFC`), nimmt Claude womöglich deinen Chrome statt des Browsers der App; Sessions dieses Accounts zeigen dann oben einen Hinweis. *Ausschalten* startet Sessions aus der App ab da mit `--no-chrome`, Claude Codes eigene Einstellung bleibt, wie sie ist. Die Session, in der du es ausschaltest, startet auf Wunsch (*Jetzt neu starten*) gleich neu und macht mit ihrem Verlauf weiter; arbeitet Claude gerade, fragt die App vorher. Ein- und ausschalten lässt sich das alles unter Einstellungen › Werkzeuge › Browser, es gilt für neu gestartete Sessions. *Ohne Nachfrage bedienen* (Standard an) erlaubt Claude die Browser-Werkzeuge im Voraus, ausgeschaltet fragt Claude Code wie bei anderen Werkzeugen.
- **Werkzeuge für die App**: Über denselben MCP-Server bekommen Sessions aus der App Werkzeuge für Claude Manager selbst, einzeln schaltbar unter Einstellungen › Werkzeuge › Claude Manager. *Eigene Limits lesen* (Standard an): Claude sieht die 5-Stunden- und Wochenlimits des Accounts, über den die Session läuft, mit Reset-Zeiten, dazu die Auslastung der anderen Accounts. *Sessions durchsuchen* (Standard an): Volltextsuche durch frühere Sessions aller Accounts, auf Wunsch nur in einem Ordner, und den Verlauf einer gefundenen Session lesen, etwa um nachzusehen, wie etwas schon einmal gelöst wurde. *Themes erstellen* (Standard an): Auf Wunsch erstellt und ändert Claude eigene Themes, dieselben Dateien wie aus dem Theme-Editor, mit Kontrastprüfung, und wechselt das Theme der App; von sich aus nie, und Claude Code fragt vor jeder Änderung um Erlaubnis. *Shell-Tabs steuern* (Standard aus): Claude öffnet Shells als Teil seines Tabs, startet darin Befehle wie den Dev-Server, sieht deren Ausgabe und schließt sie wieder; nur Shells, die die Session selbst geöffnet hat. Weil diese Befehle an Claude Codes Berechtigungen vorbeilaufen, fragt Claude Code vor jedem Aufruf, außer *Ohne Nachfrage* ist an. Lesen von Limits, Sessions und Themes ist ohne Nachfrage erlaubt.
- **Claude kennt die App**: Jede Session, die die App startet, weiß, dass sie in Claude Manager läuft. Die App hängt Claude Codes Systemprompt eine kurze Beschreibung ihrer Oberfläche an (Tabs, geteilte Tabs, Browser, Accounts, Seiten und Einstellungen samt ihren deutschen Namen), als Datei `claude-context.md` im Datenordner der App über `--append-system-prompt-file`. So versteht Claude, was mit „dem Tab“, „dem Browser daneben“ oder „Einstellungen › Werkzeuge“ gemeint ist, und kann sagen, wo etwas zu finden ist. Sehen tut man davon nichts, und Claude spricht es nicht von sich aus an. Claude Code schickt den Systemprompt mit jeder Anfrage, die Beschreibung kostet also jedes Mal rund 400 Tokens, meist aus dem Prompt-Cache. Wer sie sparen will, schaltet sie unter Einstellungen › Werkzeuge › Claude Manager › *Claude kennt die App* ab (Standard an); das gilt für Sessions, die danach starten. Ein eigenes `--append-system-prompt` in den Startoptionen gilt ab Claude Code 2.1.283 zusätzlich, bei älteren Versionen statt der Beschreibung; eine eigene `--append-system-prompt-file` immer statt ihr.
- **Übersicht**: alle Tabs auf einen Blick, als Karten nach Zustand: oben die, in denen Claude auf dich wartet (Erlaubnis, Frage, Plan oder Limit) mit dem wartenden Befehl oder der Frage, dann die, in denen Claude arbeitet, mit dem Werkzeug und seinen Subagents, dann die fertigen mit dem Anfang der letzten Antwort. Jede Karte zeigt Ordner, Modell, den letzten Prompt, wie voll der Kontext ist und das 5-Stunden-Limit des Accounts. Ein Klick öffnet den Tab, Strg+Umschalt+J springt von überall zum nächsten wartenden, ein Punkt in der Leiste links zählt sie. Den letzten Prompt und die Werkzeuge kennt die App über die Hooks (Einstellung *Zustand über Hooks melden*).
- **Sessions**: alle gespeicherten Claude-Code-Sessions, gruppiert nach Account. Suche über Titel, ersten und letzten Prompt, Ordner, Git-Branch und Session-ID, Verlauf mit Markdown und Tool-Aufrufen, die sich aufklappen lassen: vollständige Eingabe und Ergebnis, Fehler rot markiert. Lange Verläufe zeigen zuerst die letzten 600 Nachrichten, ganz oben holt *600 ältere laden* (zuletzt *Alle älteren laden*) die davor, ohne dass die Ansicht springt. Trenner zeigen, an welchem Tag geschrieben wurde (Heute, Gestern, Wochentag und Datum). Fortsetzen per Doppelklick oder als neue Session abzweigen (`--fork-session`). Läuft die Session schon in einem Tab, kommt dieser Tab nach vorne; hat ein Claude Code außerhalb der App sie offen, fragt die App vorher, damit nicht zwei Prozesse in denselben Verlauf schreiben. Filter zeigen nur Sessions der letzten Tage oder solche, die älter sind als eine Woche bis ein Jahr, und nach Größe des Verlaufs die großen (über 1, 10 oder 50 MB) oder die fast leeren (unter 10 KB bis 1 MB). Anzahl und Gesamtgröße der gefilterten Sessions stehen daneben. Filter und Sortierung der Ordner bleiben, wie man sie verlassen hat, auch über einen Neustart. Mit *Mehrere auswählen* (oder Strg+Klick) lassen sich Sessions markieren, mit Umschalt+Klick als Bereich (nur, was die Liste zeigt, nicht was noch hinter *Weitere anzeigen* steckt), und gesammelt löschen, einzelne auch über das Kontextmenü. Sie kommen samt Subagents und `/rewind`-Ständen in den Papierkorb und lassen sich dort wiederherstellen. Sessions, die in einem Tab offen sind oder gerade in Claude Code laufen, bleiben. *Verschieben nach* im Kontextmenü legt eine Session in einen anderen Ordner, wie `/cd` in Claude Code: zur Wahl stehen die Projekte der Workspaces oder ein beliebiger Ordner. Läuft sie in einem Tab, startet sie dort nach einer Rückfrage im neuen Ordner neu (nicht abgeschickte Eingaben gehen verloren); solange Claude arbeitet, ist der Eintrag ausgegraut. Der Token-Verbrauch im Dashboard wird aus den Transcripts berechnet, gelöschte Sessions fehlen dort danach.
- **Usage-Dashboard**: 5-Stunden- und Wochen-Limits (live, wie bei [cswap](https://github.com/realiti4/claude-swap), auch für Accounts, die gerade nicht genutzt werden: ihr abgelaufener Zugangstoken wird dafür erneuert) sowie Token-Verbrauch pro Tag und Modell, berechnet aus den lokalen Transcripts. Ist der Login von `~/.claude` schon als eigener Account hinterlegt (etwa nach dem cswap-Import), lassen Dashboard und Accounts-Seite den Account „Standard“ weg, damit dieselben Limits nicht doppelt erscheinen. Auf der Accounts-Seite lässt er sich über den Hinweis unter den Karten wieder einblenden. Die Limits des Accounts im aktiven Tab stehen außerdem in der Titelleiste, ein Klick zeigt Details und Reset-Zeiten. Balken und Ringe sind grün (unter 60 %), orange (ab 60 %) und rot (ab 85 %), in den Farben des gewählten Themes.
- **Artefakte**: die Seiten und Dokumente, die Claude mit dem Artifact-Tool auf claude.ai veröffentlicht hat, für jeden Account mit Login, als Karten wie auf claude.ai: Vorschaubild, Titel, Besitzer, wann zuletzt angesehen, Aufrufe und wer es öffnen darf. Mit Suche und Filtern (Eigene, Geteilt, Angepinnt). Ein Klick öffnet es im Browser. Das Menü kopiert den Link, zeigt die Session, in der Claude es veröffentlicht hat, pinnt es in der Seitenleiste von claude.ai an und benennt eigene um oder löscht sie (mit Rückfrage). Accounts mit API-Key haben keine Artefakte.
- **Befehl `cm`**: öffnet eine Claude-Session im Manager, aus jedem Terminal oder unter Windows direkt aus der Explorer-Adressleiste (siehe unten).
- **Darstellung**: unter Windows Acryl, Mica oder Mica Alt, auch wenn das Fenster nicht im Fokus ist (unter Linux ist das Fenster deckend). 11 Themes (u. a. Catppuccin, Tokyo Night, Rosé Pine, Nord, Dracula) und eigene: Unter Einstellungen › Darstellung › Theme legt man ein neues an oder kopiert ein eingebautes und ändert es im Theme-Editor. Der erklärt jede Farbe, wofür sie da ist, mit Farbwähler (auch Pipette), Suche über Namen, Schlüssel, Beschreibung und Wert, einem Hinweis bei zu wenig Kontrast und einer Vorschau von App und Terminal in den eigenen Farben; er schließt sich nicht aus Versehen, ungespeicherte Änderungen fragen nach. Eigene Themes sind übersichtliche JSON-Dateien im Ordner `themes` der App-Daten (Farben der App, des Terminals und seiner 16 ANSI-Farben getrennt), die sich auch im Standardprogramm bearbeiten, exportieren, importieren (auch per Drag & Drop) und löschen lassen. Die App beobachtet den Ordner: Hineinkopierte, anderswo geänderte und gelöschte Themes erscheinen sofort, fehlt die Datei des gewählten Themes, gilt bis zu ihrer Rückkehr das Standard-Theme. Das Terminal folgt dem Theme oder bekommt ein eigenes Farbschema. Claude Codes Theme „Auto (match terminal)“ folgt mit, auch beim Wechsel zwischen hell und dunkel in einer laufenden Session. Schrift, Größe, Zeilenhöhe, Cursor usw. lassen sich mit Live-Vorschau einstellen. Schriften mit Ligaturen wie JetBrains Mono, Fira Code oder Cascadia Code zeigen `=>` als ⇒ und `!=` als ≠ (abschaltbar unter Einstellungen › Terminal › Schrift › Ligaturen). Blockzeichen wie die Krabbe von Claude Code stehen auch mit dem DOM-Renderer ohne Lücken da. Seitenleisten von Claude Code wie `/diff` bekommen statt ihres festen Graus die Flächenfarbe des Themes oder den Terminal-Hintergrund (Einstellungen › Terminal). Die Krabbe von Claude Code erscheint in der Akzentfarbe des Themes, auch wenn sie sich bewegt (abschaltbar unter Einstellungen › Terminal › Claude-Logo). Die Tabs stehen wahlweise oben in der Titelleiste, untereinander in der Seitenleiste (deren Symbole dann auch beschriftet sind) oder in Gruppen wie die Editorgruppen von VS Code (Einstellungen › Darstellung › Tabs). In Gruppen hat jeder Teil des geteilten Fensters seine eigene Tab-Leiste; Tabs lassen sich in eine andere Gruppe ziehen oder an deren Rand, um sie zu teilen, und Einstellungen, Usage-Dashboard, Sessions und Accounts öffnen als Tabs in der ersten Gruppe. Ein Browser gehört dort immer zu einer Session, und alle Sessions teilen sich einen Browser-Tab, den man wie jeden Tab verschieben und teilen kann (beim ersten Mal öffnet er rechts neben der Session): Er zeigt immer die Seiten der Session, die gerade die Tastatur hat, trägt den Titel der Seite, die er zeigt, und kommt mit der Session nach vorn. Mehrere Seiten einer Session stehen als kleine Tabs in seiner Leiste, das Plus öffnet eine weitere; hat die Session noch keine, steht dort ein Adressfeld. Die Seiten der anderen Sessions laufen unsichtbar weiter, auch wenn Claude dort arbeitet, ein Punkt am Session-Menü links in der Leiste zeigt das. Über dieses Menü schaut man in den Browser einer anderen Session, bis die nächste Session die Tastatur bekommt. Schließt man den Browser-Tab, bleiben die Seiten; er kommt mit der nächsten Seite oder über *Browser öffnen* wieder. Zeigt er gerade die Seiten einer Session, steht in ihren Menüs *Browser schließen*; für jede andere Session *Browser öffnen*, das ihn nach vorn holt und ihre Seiten oder das Adressfeld zeigt. Seiten aus dem letzten Lauf laden erst, wenn man sie ansieht oder Claude sie braucht. Browser ohne Session (etwa aus einem anderen Modus) bleiben eigene Tabs. Beim Wechsel zwischen den Modi bleiben Tabs und Aufteilung erhalten.

Schieberegler in den Einstellungen nennen ihren Namen und Wert. Die Trennlinien (Breite des Dateibaums und der Änderungen, Teile eines geteilten Tabs, Gruppen) lassen sich mit Tab erreichen und mit den Pfeiltasten verschieben, mit Umschalt in größeren Schritten. Pos1 und Ende schieben sie bis an den Rand, Enter setzt sie zurück wie ein Doppelklick. Accounts und Anmeldedaten gehören nicht dazu, auch der Account für neue Sessions bleibt, wie er ist. Pfade zur `claude.exe` oder zum Standard-Arbeitsordner, die es auf diesem Computer nicht gibt, werden nicht übernommen. Einstellungen, die die Datei nicht kennt (z. Direkt nach dem Import lässt er sich in der Meldung rückgängig machen.

Eine Windows-Benachrichtigung (unter Linux die des Desktops) nennt Tab und Ereignis, auf Wunsch mit dem Anfang der Antwort, dem Befehl, der auf Erlaubnis wartet, oder Claudes Frage; ein Klick öffnet den Tab. Dazu blinkt die Taskleiste, und Tabs mit Neuigkeiten, die du noch nicht gesehen hast, bekommen einen Punkt (orange, wenn Claude auf dich wartet). Alles ist einstellbar unter *Einstellungen › Benachrichtigungen*: welche Ereignisse, ob nur bei Fenster im Hintergrund oder auch, wenn ein anderer Tab offen ist, eine Mindestdauer für fertige Antworten, Vorschau, Ton, Blinken und Punkt. Erreicht ein Limit eines Accounts eine einstellbare Schwelle (Standard 80 %), kommt eine Warnung mit Account, Limit und Reset-Zeit, einmal pro Account und Zeitraum, auch über einen Neustart hinweg; ein Klick öffnet das Usage-Dashboard. Die Glocke oben rechts in der Titelleiste schaltet alles mit einem Klick an und aus, einzelne Tabs lassen sich über ihr Kontextmenü stummschalten. Sessions aus der App melden ihren Zustand über Claude Codes Hooks (*Einstellungen › Werkzeuge › Zustand über Hooks melden*, standardmäßig an): Der Hinweis kommt im selben Moment, in dem Claude fertig ist oder fragt, und die Infokarte des Tabs zeigt, welches Werkzeug gerade läuft (z. B. den Befehl), wie viele Subagents arbeiten und ob Claude den Verlauf zusammenfasst. Wartet Claude auf einen Subagent im Hintergrund, kommt „fertig“ erst nach dessen Ergebnis. Ohne Hooks (ausgeschaltet, ältere Version, Hooks per Richtlinie gesperrt) erkennt die App das Ende eines Turns am Fenstertitel, den Claude Code setzt (`◐`/`◑` beim Arbeiten, `✳` im Leerlauf), der Grund steht im Transcript. Weil Claude Code dort gepuffert schreibt, kommt der Hinweis dann 1 bis 5 Sekunden nach dem Ende.

Für den Tab mit der Tastatur bietet sie, was sein Kontextmenü kann: umbenennen, in einem geteilten Tab einen Teil maximieren, neu starten, Prozess beenden, stummschalten, Ordner öffnen, mit einem anderen Account weitermachen und schließen. ## Installation

Die Dateien stehen bei jedem [Release](https://github.com/qzconnor/claude-manager/releases/latest) auf GitHub.

- **Windows 11**: `Claude-Manager-<version>-Setup.exe` ausführen.
- **Debian, Ubuntu, Linux Mint, Pop!_OS**: `sudo apt install ./Claude-Manager-<version>.deb`. Die App steht danach im Anwendungsmenü und unter `/opt/Claude Manager`, auf der Kommandozeile als `claude-manager`.
- **Fedora, openSUSE, RHEL**: `sudo dnf install ./Claude-Manager-<version>.rpm` (openSUSE: `sudo zypper install ./…`).
- **Alle anderen Distributionen**: `Claude-Manager-<version>.AppImage` herunterladen, mit `chmod +x Claude-Manager-*.AppImage` ausführbar machen und starten. Es braucht kein libfuse2, nur FUSE 3 (`fusermount3`), das jede aktuelle Distribution mitbringt. Ins Anwendungsmenü kommt es z. B. mit [Gear Lever](https://flathub.org/apps/it.mijorus.gearlever) oder AppImageLauncher.

Updates holt sich die App selbst: Das AppImage ersetzt seine eigene Datei, das deb- und rpm-Paket installiert die App über den Paketmanager, der dafür einmal nach dem Passwort fragt.

## Befehl `cm`

Der Installer richtet den Befehl `cm` ein, unter Linux die App bei ihrem ersten Start. Wie `cmd` funktioniert er auch in der Adressleiste des Explorers: `cm` eintippen, Enter, und im Manager öffnet sich eine Session im angezeigten Ordner. Läuft die App noch nicht, startet sie. Ist der Ordner schon in einem Tab offen, wechselt `cm` nur zu diesem Tab, auch wenn er gerade beim Start wiederhergestellt wurde (abschaltbar unter *Einstellungen → Claude Code*).

| Aufruf | Wirkung |
|---|---|
| `cm` | Session im aktuellen Ordner mit dem Account für neue Sessions |
| `cm <ordner>` | Session in `<ordner>` (relativ zum aktuellen Ordner, `~` = Benutzerordner) |
| `cm -a <account>` | mit Account: Name, E-Mail, ID oder ein eindeutiger Teil des Namens |
| `cm -c` | letzte Session in diesem Ordner fortsetzen (`claude --continue`) |
| `cm -r [session-id]` | Session fortsetzen, ohne ID mit der Auswahl von Claude Code |
| `cm -s` | PowerShell (Linux: die Login-Shell) mit der Umgebung des Accounts statt Claude Code |
| `cm -n` | immer einen neuen Tab öffnen, auch wenn der Ordner schon offen ist |
| `cm -- <argumente>` | Argumente an `claude` weitergeben, z. B. `cm -- --model opus` |
| `cm -h` | Hilfe |

Mit `cm --` weitergegebene Optionen wie `--model opus` oder `--add-dir` behält der Tab, wenn die Session den Account wechselt, neu startet, in einen anderen Ordner zieht oder beim nächsten App-Start wiederhergestellt wird. Ein mitgegebener Prompt wird dabei nicht noch einmal geschickt. Optionen, die nur für den ersten Start gelten (`--continue`, `--resume`, `--session-id`, `--name`, `--worktree`), entfallen ebenfalls, weil die Session ihren Verlauf, Namen und Worktree schon hat.

Technisch ist `cm.exe` ein kleiner Launcher (`src/launcher/cm.cs`), der Ordner und Argumente an die laufende App weiterreicht. Er liegt im Unterordner `bin` der Installation, nur dieser Ordner kommt in den Benutzer-PATH. Für die Explorer-Adressleiste trägt der Installer zusätzlich einen App-Pfad unter `HKCU\Software\Microsoft\Windows\CurrentVersion\App Paths\cm.exe` ein. Admin-Rechte braucht beides nicht. Die Deinstallation entfernt beides wieder, der restliche PATH bleibt unverändert. In *Einstellungen → Claude Code* lässt sich der Befehl auch nachträglich an- und abmelden.

Unter Linux schreibt die App ein kleines Shell-Skript nach `~/.local/bin/cm` (`src/main/cli/linux-launcher.ts`). Es enthält den Pfad der App, beim AppImage den der AppImage-Datei, und die App hält ihn bei jedem Start aktuell, auch wenn das AppImage verschoben wurde. Ein `cm` eines anderen Programms überschreibt sie nie. `~/.local/bin` steht bei den meisten Distributionen im PATH, sonst weist die Einstellungsseite darauf hin. Hast du den Befehl dort abgemeldet, richtet ihn auch ein späterer Start nicht wieder ein.

## Account wechseln, wenn ein Limit erreicht ist

Die App merkt, wenn Claude Code in einem Tab an ein Nutzungslimit stößt: Der Tab bekommt ein Warnsymbol, und oben im Terminal steht, welches Limit es ist und wann es zurückgesetzt wird. Ein Klick auf „Mit … fortsetzen“ beendet Claude Code im Tab und setzt dieselbe Session sofort mit dem anderen Account fort. Dasselbe geht jederzeit über das Tab-Kontextmenü (*Account wechseln*) und in *Sessions* über den Pfeil neben *Fortsetzen*.

- **Token- und API-Key-Accounts** leihen der Session nur ihren Schlüssel. Die Session bleibt, wo sie ist (gleiche ID, gleicher Verlauf, `/rewind` geht weiter), und läuft über die Limits des anderen Accounts. Der Tab zeigt den neuen Account, der Tooltip, wo die Session gespeichert ist.
- **Browser-Logins** (Standard, eigener Login) funktionieren nur im eigenen Ordner, weil Claude Code den Login dort erneuert. Die Session wird deshalb dorthin kopiert (Verlauf, Unterordner, `/rewind`-Stände) und läuft dort weiter. Beim bisherigen Account bleibt der Stand bis zum Wechsel. Liegt beim Ziel schon ein neuerer Stand derselben Session, bricht die App ab, ohne den Tab anzutasten.

Vorgeschlagen wird zuerst ein Account, der ohne Kopie übernehmen kann; Accounts am Limit oder ohne Anmeldung stehen am Ende. Woher die App das weiß: Claude Code schreibt ein erreichtes Limit mit Typ und Reset-Zeit ins Transcript, und unter `<config>/sessions/<pid>.json` steht, welche Session ein Prozess gerade offen hat. Neue Sessions startet die App mit `--session-id`, damit jeder Tab seine Session von Anfang an kennt.

Accounts mit demselben Login (etwa der Account „Standard“ und sein Gegenstück aus cswap) teilen ihre Limits und gelten zusammen als erschöpft.

**Automatisch wechseln** (*Einstellungen › Claude Code › Bei einem Limit automatisch wechseln*, standardmäßig aus): Stößt eine Session an ein Limit, läuft sie sofort mit dem vorgeschlagenen Account weiter, ohne Klick und auch, wenn das Fenster im Infobereich liegt. Der neue Tab nimmt den Platz des alten ein. Die Benachrichtigung meldet dann statt „Limit erreicht“, mit welchem Account es weitergeht, oder warum der Wechsel nicht ging. Einen Account, den die App wegen seines Limits verlassen hat, wählt sie bis zu dessen Reset nicht wieder, auch wenn sein Tab längst zu ist oder die App neu gestartet wurde (ohne bekannte Reset-Zeit fünf Stunden lang). So wechseln zwei volle Accounts nie hin und her. Ist kein Account frei, bleibt der Hinweis im Tab, und die Session wartet: Sie wechselt, sobald ein Account frei wird (etwa wieder angemeldet oder nach dessen Reset), oder macht kurz nach dem Reset ihres eigenen Limits mit ihrem Account weiter, samt der Nachricht nach dem Wechsel. Kennt die App keinen Reset und wird kein Account frei, bleibt sie stehen.

Stand die Session am Limit, schickt die App nach dem Wechsel „Mach weiter“, damit Claude ohne Eingabe dort weitermacht, wo es aufgehört hat. Die Nachricht lässt sich unter *Einstellungen › Claude Code* ändern oder leeren (dann wird nichts geschickt). Beim Wechsel ohne Limit wird nie etwas geschickt. Was noch ungesendet im Eingabefeld stand, geht beim Wechsel verloren, weil Claude Code dafür beendet wird.

Die erste Antwort nach dem Wechsel kostet etwas mehr, weil der Prompt-Cache pro Account gilt und der andere Account den Verlauf einmal neu einliest.

## Account-Arten

| Art | Wie Claude Code gestartet wird | Usage-Limits |
| --- | --- | --- |
| **Standard** | normaler Login in `~/.claude` | live |
| **Eigener Login (OAuth)** | eigener Ordner unter `<userData>/profiles/<id>` als `CLAUDE_CONFIG_DIR`, Anmeldung im Browser per `claude auth login` | live |
| **Long-lived Token** | `CLAUDE_CODE_OAUTH_TOKEN=<Token aus claude setup-token>` | nicht abrufbar (die Usage-API lehnt diesen Token-Typ ab); lokale Statistik geht |
| **API-Key** | `ANTHROPIC_API_KEY=<sk-ant-api…>` | nicht zutreffend (Abrechnung nach Verbrauch) |

Bei Browser-Logins fragt die App Anthropic, zu welchem Konto und welcher Organisation der aktuelle Login gehört (`/api/oauth/profile`, eine Anfrage pro Zugangstoken). So stehen zwei Logins mit derselben E-Mail getrennt da, z. B. „name@firma.de · Firma“ (Team) und „name@firma.de · Persönlich“ (Pro/Max). Der Block `oauthAccount` in Claude Codes Konfiguration reicht dafür nicht: Wechselt ein Tool wie cswap den Login, kann eine noch laufende Claude-Code-Instanz den alten Block zurückschreiben. Wechselt der Login in einem Ordner, verwirft die App die alten Usage-Werte und fragt sofort neu ab.

Neue OAuth-Profile können `settings.json`, `keybindings.json`, `CLAUDE.md`, `skills`, `commands`, `agents` und `rules` aus `~/.claude` übernehmen. Sie werden einmalig kopiert, nicht verlinkt.

### Accounts aus cswap übernehmen

Ist [cswap](https://github.com/realiti4/claude-swap) installiert und kennt Accounts, zeigt die Accounts-Seite „Aus cswap importieren“. Ohne cswap erscheint der Knopf nicht. Die App liest dafür nur cswaps `sequence.json` (Alias, E-Mail, Organisation) und legt für jeden gewählten Account einen eigenen Browser-Login an. Name ist der Alias, sonst die E-Mail. Accounts, die es in der App schon gibt, sind markiert und nicht wählbar.

Danach meldest du jeden Account einmal über „Anmelden“ an, die E-Mail ist auf der Login-Seite schon eingetragen. cswaps gespeicherte Zugangsdaten liest die App nicht: Ein Refresh-Token lässt sich nur einmal verwenden, zwei Kopien desselben Logins würden sich gegenseitig abmelden. Gehört die E-Mail zu mehreren Organisationen und meldest du dich mit der falschen an, weist die Karte darauf hin. „Neu anmelden“ korrigiert das, „Ignorieren“ behält den Login.

## Sicherheit

- Tokens und API-Keys werden mit Windows DPAPI bzw. unter Linux mit dem Schlüsselbund verschlüsselt gespeichert (Electron `safeStorage`), nie im Klartext. Unter KDE ist das KWallet, auf allen anderen Desktops der Secret Service (GNOME Keyring, KeePassXC u. a.), auch dort, wo Chromium ihn von sich aus nicht nimmt (sway, Hyprland, i3, MATE, LXQt). Mit `--password-store=…` lässt sich das wie in Chromium überschreiben. Gibt es unter Linux keinen Schlüsselbund, speichert die App keine Tokens und API-Keys, statt auf Chromiums festen Schlüssel auszuweichen. Browser-Logins brauchen keinen, ihre Zugangsdaten verwaltet Claude Code selbst. Entschlüsselt werden sie einmal beim Start und nur im Speicher des Hauptprozesses gehalten. Die UI und die API zeigen nur eine maskierte Vorschau.
- Die App liest OAuth-Zugangsdaten nur, um die Usage und den Inhaber des Logins abzufragen und die Artefakte des Logins aufzulisten und zu verwalten. Der Token geht dabei nur an `api.anthropic.com`, Weiterleitungen folgt die App nicht. Die Vorschaubilder der Artefakte lädt sie ohne Token und nur von Adressen auf `frame.claudeusercontent.com`, die in der zuletzt geladenen Liste stehen. Ist der Zugangstoken eines Browser-Logins abgelaufen, erneuert sie ihn mit dem Refresh-Token, so wie Claude Code beim Start einer Session: unter Claude Codes eigener Sperre für den Ordner (`.oauth_refresh.lock`), und geschrieben wird nur, wenn in `.credentials.json` noch derselbe Refresh-Token steht. So verwenden App und Claude Code nie denselben Refresh-Token zweimal. Sonst verändert die App die Zugangsdaten nicht. Im Cache steht nur ein Hash des Tokens, nicht der Token.
- Seiten im Browser laufen in einer Sandbox ohne Node.js und ohne die Brücke `window.api`, in einem eigenen Profil (`persist:browser`), getrennt von der App. Sie dürfen nur http- und https-Adressen laden, Weiterleitungen auf andere Schemas (`file:`, `javascript:` …) werden blockiert. Popups (etwa „Mit Google anmelden“) öffnen sich als kleines eigenes Fenster ohne Adressleiste, ihr Titel nennt die Seite, und sie dürfen nur, was ihre Seite darf; andere neue Fenster gibt es nicht. Berechtigungen wie Kamera, Mikrofon, Standort oder Benachrichtigungen werden abgelehnt, nur das Kopieren in die Zwischenablage ist erlaubt. Den Seiten gegenüber meldet sich der Browser als gewöhnliches Chrome, ohne Electron und App im User-Agent. Passwörter speichert er nicht, Cookies liegen wie bei Chrome verschlüsselt auf der Platte (DPAPI bzw. Schlüsselbund, gesetzt beim Bauen über die Electron-Fuse `EnableCookieEncryption`; bei `npm run dev` gilt sie nicht).
- Den Browser für Claude bekommen nur Sessions, die die App startet, über `--mcp-config` und `--allowedTools` beim Start. `~/.claude` und andere Claude-Code-Instanzen bleiben unberührt. Der MCP-Server lauscht nur auf `127.0.0.1` an einem zufälligen Port, jede Session hat einen eigenen zufälligen Token, der mit ihr erlischt. Ihre Konfigurationsdatei unter `<userData>/browser-mcp` verschwindet, sobald die Session endet. Anfragen mit fremdem `Host`-Header oder mit `Origin` (also aus einer Webseite) lehnt der Server ab. Eine Session bedient den Browser in ihrem Tab, die Browser, die sie selbst geöffnet hat, und deine eigenen, die keiner Session gehören (so steht es auch in den Anweisungen, die Claude vom MCP-Server bekommt), nie die einer anderen Session. Die Seite steuert sie über das DevTools-Protokoll des jeweiligen Browsers, nicht über die App. Passwortfelder sieht Claude im Baum der Seite und auf Screenshots nur als Punkte. Header einer Anfrage zeigt die App Claude ohne die Werte von Cookies, `Set-Cookie`, `Authorization` und ähnlichen Schlüsseln, den Inhalt einer Anfrage ohne die Werte von Passwort- und ähnlichen Feldern (Formulare, JSON), beim Löschen der Daten einer Seite nur die Namen der Cookies, und von httpOnly-Cookies (meist Logins, die alle Sessions im gemeinsamen Profil teilen) zeigt `browser_storage` Namen und Eigenschaften, nicht den Wert. Die Werkzeuge für die App gehen nur an die Session selbst: Shells, die sie nicht geöffnet hat, sieht und bedient sie nicht, und `--allowedTools` nennt jedes Werkzeug einzeln, damit Claude Code für die Shells weiter fragt. Weil sich `--allowedTools` einer laufenden Session nicht zurücknehmen lässt, fragt die App selbst vor jeder Aktion, wenn du *ohne Nachfrage* ausschaltest, während die Session läuft. Was die Seite sonst zeigt, steht wie alles, was Claude liest, im Transcript der Session; ein Passwort, das du Claude im Chat gibst, also auch. Mit *Übernehmen* meldest du dich selbst an: Claude handelt nicht, bis du zurückgibst, und was die Seite in dieser Zeit sendet und empfängt, kommt nicht ins Protokoll der Anfragen, das Claude liest. Danach liest Claude die Seite neu ein und sieht, was sie dann zeigt (Passwortfelder nur als Punkte). Was die Seite selbst in ihre Konsole schreibt, sieht Claude auch aus dieser Zeit.
- Die Hooks für den Zustand bekommen ebenfalls nur Sessions, die die App startet: über eine Settings-Datei pro Session (`--settings`, unter `<userData>/session-hooks`, nur für den eigenen Benutzer lesbar), die mit der Session verschwindet. In `~/.claude` und die Einstellungen des Projekts schreibt die App nichts, eigene Hooks laufen weiter. Gibt der Nutzer selbst `--settings` mit, führt die App seine Einstellungen mit ihren Hooks in dieser Datei zusammen, weil Claude Code von mehreren `--settings` nur das letzte nimmt. Die Hooks gehen per HTTP an denselben Server wie der MCP-Server (eigener Pfad, eigener Token pro Session), die App antwortet sofort und leer: Sie entscheidet nichts und fügt Claudes Kontext nichts hinzu.
- Token- und API-Key-Accounts geben ihr Secret über die Umgebung an Claude Code (`CLAUDE_CODE_OAUTH_TOKEN` bzw. `ANTHROPIC_API_KEY`). Damit erben es auch die Befehle, die Claude ausführt. Unter Einstellungen › Claude Code › *Token und API-Key vor Befehlen verbergen* entfernt Claude Code es dort (aus Bash, Hooks und MCP-Servern); Claude Code startet dann aber immer im normalen Berechtigungsmodus.
- Das Fenster der App bekommt außer der Zwischenablage keine Berechtigungen. Der Hauptprozess nimmt Nachrichten nur von den Fenstern der App an, nicht von Browser-Tabs, ihren Popups oder Frames in einer Seite. Im installierten Programm sind `NODE_OPTIONS` und `--inspect` abgeschaltet (Electron-Fuses), und es startet nur aus seinem eigenen `app.asar`.
- Der Dateibaum fragt Git nur, er führt nichts aus, was das Repository selbst einstellt: Für seinen Git-Status und seine Diffs startet Git weder ein fsmonitor-Programm noch Filter, textconv oder externe Diff-Programme aus der Konfiguration des Repositorys. Ein Ordner, der samt `.git` von woanders kommt (etwa aus einem Archiv), kann so beim Aufklappen nichts starten. Filter aus der eigenen Git-Konfiguration (Git LFS) bleiben.
- Die lokale API ist standardmäßig aus. Eingeschaltet lauscht sie nur auf `127.0.0.1`, verlangt einen zufälligen Bearer-Token (ebenfalls verschlüsselt, ohne Schlüsselbund gilt er nur bis zum Beenden) und lehnt fremde `Host`-Header ab (Schutz vor DNS-Rebinding).

## Voraussetzungen

- Windows 11 22H2 oder neuer für Acryl/Mica. Mit der Material-Einstellung *Aus* ist der Hintergrund deckend.
- Linux x64 mit X11 oder Wayland, z. B. Ubuntu 22.04, Debian 12, Fedora 40 oder neuer. Das Symbol im Infobereich zeigt GNOME erst mit der Erweiterung „AppIndicator“ (bei Ubuntu dabei).
- [Claude Code](https://docs.claude.com/en/docs/claude-code) installiert. Der Pfad wird automatisch erkannt oder in *Einstellungen → Claude Code* gesetzt.
- Für die Entwicklung: Node.js 22 oder neuer.

## Entwicklung

```powershell
npm install
npm run dev          # App mit Hot Reload starten
npm run typecheck    # Main/Preload (tsc) und Renderer (vue-tsc) prüfen
npm test             # Unit-Tests (Vitest), `npm run test:watch` läuft bei Änderungen mit
npm run build:win    # Typecheck, Build, cm.exe und NSIS-Installer → release/<version>/
npm run build:linux  # unter Linux: Typecheck, Build, AppImage, deb und rpm → release/<version>/
```

Die Linux-Pakete lassen sich nur unter Linux bauen, weil node-pty dort keine fertigen Binärdateien mitbringt: `npm install` kompiliert es (dafür `python3`, `make` und `g++`; `allowScripts` in der package.json erlaubt das auch unter npm 12, das Install-Skripte sonst blockiert), für das rpm-Paket braucht es zusätzlich `rpmbuild` (Paket `rpm`). Ohne Linux-Rechner geht es z. B. in WSL oder im Container `node:24-bookworm`.

Die Tests liegen als `*.test.ts` neben ihrem Modul und prüfen die Logik, die ohne Electron und Fenster auskommt: Parser für Transcripts, Fenstertitel und die Usage-API, Regeln wie die Limit-Warnung, Hilfsfunktionen und Themes. Beispieldaten sind kleine, anonymisierte Ausschnitte im Format von Claude Code. CI führt sie bei jedem Pull Request unter Windows und Linux aus.

`npm run dev` und `npm start` nutzen ein eigenes Profil (`%APPDATA%\Claude Manager Dev`), damit sie neben der installierten App laufen. Einstellungen und Accounts sind dort getrennt, der Account „Standard“ (`~/.claude`) ist immer da.

`npx electron-builder --win --dir` erzeugt nur den entpackten Ordner `release/<version>/win-unpacked`. Das reicht zum schnellen Testen. Vorher einmal `npm run build:launcher` ausführen, das kompiliert `cm.exe` mit dem C#-Compiler aus dem .NET Framework 4, der bei Windows dabei ist.

### Releases

Jeder Push auf `master` startet [semantic-release](https://semantic-release.gitbook.io/) (`.github/workflows/release.yml`). Es liest die Version aus den Commit-Nachrichten ([Conventional Commits](https://www.conventionalcommits.org/de/)). Mit ihr bauen ein Windows- und ein Linux-Runner den Installer bzw. AppImage, deb und rpm, danach veröffentlicht semantic-release alles zusammen mit den Versionshinweisen als GitHub-Release. Von dort holt sich die installierte App ihre Updates.

| Commit | Version | Versionshinweise |
| --- | --- | --- |
| `feat: …` | neue Minor-Version | „Neue Funktionen“ |
| `fix: …` | neue Patch-Version | „Fehlerbehebungen“ |
| `perf: …` | neue Patch-Version | „Schneller“ |
| `feat!: …` oder `BREAKING CHANGE:` im Text | neue Major-Version | |
| `docs:`, `ci:`, `build:`, `chore:`, `refactor:`, `style:`, `test:` | kein Release | nicht aufgeführt |

Pull Requests per Squash-Merge zusammenführen: Dann wird ihr Titel zur Commit-Nachricht und ihre Beschreibung zum Text darunter. Deshalb prüft `pr-title.yml` den Titel, und `ci.yml` baut den Installer und die Linux-Pakete einmal zur Probe. Die Version in `package.json` bleibt im Repository unverändert: semantic-release setzt sie nur für den Build.

Der Titel nennt kurz, worum es geht, und trägt den wichtigsten Typ: `feat:`, sobald eine neue Funktion dabei ist. Was in die Versionshinweise kommt, listet die Beschreibung unter `## Versionshinweise`, eine Änderung pro Zeile (Vorlage: `.github/pull_request_template.md`). Jede Zeile wird ein eigener Punkt. Zeilen ohne Typ zählen zum Typ des Titels, `fix: …` landet unter „Fehlerbehebungen“. `release.config.mjs` teilt die Liste auf (`src/shared/release-notes.ts`). Ohne diese Liste wird der Titel zum Punkt, mehrere Änderungen darin trennt `; `. Die App teilt so auch ältere Versionshinweise auf, und „Details“ zeigt den Rest der Beschreibung.

## Technische Hinweise

- **Acryl ohne Fokus**: Windows schaltet das Backdrop-Material ab, sobald ein Fenster inaktiv wird. Direkt nach dem Deaktivieren schickt die App `WM_NCACTIVATE` mit „aktiv“ an das eigene Fenster (`SendMessageW` über koffi). DWM zeichnet das Material dann weiter, ohne dass die App den Fokus stiehlt. Ist koffi nicht verfügbar, wird das Material beim Fokuswechsel normal ausgeblendet.
- **WebGL-Kontexte**: Chromium hält pro Fenster nur etwa 16 WebGL-Kontexte und verwirft darüber den ältesten, auch den eines sichtbaren Terminals. Deshalb hat nur ein Terminal auf dem Bildschirm einen; ist es 30 Sekunden verdeckt, gibt es ihn ab und bekommt beim Zeigen einen neuen. Mehr als acht halten nie einen, die am längsten verdeckten geben zuerst ab. Geht ein Kontext verloren (etwa beim Zurücksetzen der GPU), holt sich das Terminal einen neuen, nach drei Verlusten bleibt es beim DOM-Renderer.
- **Electron 45.2.0 fest**: Ab Electron 45.2.1 (Chromium 156.0.8078.75) zeichnet xterms WebGL-Renderer die Schrift bei 200 % Skalierung nur halb so groß. Deshalb steht Electron ohne `^` in `package.json`; vor einem Update erst ein Terminal bei 200 % ansehen.
- **Blockzeichen im DOM-Renderer**: Der DOM-Renderer von xterm nimmt Blockzeichen (U+2580–U+259F) aus der Schrift, die meist nicht die ganze Zelle füllen, sodass Lücken bleiben. `lib/block-glyphs.ts` setzt jedes Blockzeichen in eine eigene Box und zeichnet seine Teile mit `::before`/`::after` über die ganze Zelle (ein MutationObserver, noch vor dem Zeichnen des Browsers). WebGL zeichnet sie selbst lückenlos.
- **Ligaturen**: xterm setzt im DOM-Renderer einen Zeichenabstand von Bruchteilen eines Pixels, und Chromium schaltet dann die Ligaturen ab; `lib/ligatures.ts` schaltet `calt` und `liga` per `font-feature-settings` wieder ein. WebGL zeichnet jede Zelle für sich, dort fasst ein Character Joiner bekannte Folgen (`=>`, `!=`, `===` …) zusammen, nicht aber lange Reihen wie `=====`. Im DOM-Renderer bleibt der Joiner aus: xterm gäbe dort jedem Zeichen einer Gruppe den Abstand der ganzen Gruppe, und bei einem Zeichenabstand über 0 rutschte die Zeile aus dem Raster.
- **xterm-WebGL-Patch**: Das WebGL-Addon malt Zellen mit Hintergrund-Flags (z. B. gedimmter Text) immer deckend in der Theme-Hintergrundfarbe. Bei unserem transparenten Terminal-Hintergrund wären das schwarze Kästen. Ein kleines Vite-Plugin in `electron.vite.config.ts` korrigiert das beim Build. Passt der Patch nach einem Update nicht mehr, bricht der Build mit einer klaren Meldung ab.
- **Umgebung unter Linux**: Aus dem Anwendungsmenü gestartet, kennt die App nur die Umgebung der Desktop-Sitzung, ohne das, was `~/.bashrc` oder `~/.zshrc` einrichten (z. B. nvm, `~/.npm-global`, `~/.bun`). Wie VS Code fragt sie deshalb beim Start einmal die Login-Shell nach ihrer Umgebung und übernimmt sie (`src/main/lib/shell-env.ts`), so findet sie `claude` auch dort. Variablen, die das AppImage nur für sich selbst setzt, bekommen Terminals nicht mit.
- **Chromium-Sandbox unter Linux**: Das deb- und rpm-Paket richten die Sandbox bei der Installation ein (unter Ubuntu 24.04 mit einem AppArmor-Profil). Das AppImage prüft beim Start, ob Benutzer-Namespaces erlaubt sind, und startet sonst ohne Sandbox, statt abzustürzen.
- **Theme „Auto“ von Claude Code**: Claude Code fragt die Hintergrundfarbe des Terminals ab (OSC 11) und hört auf Meldungen, wenn das Terminal zwischen hell und dunkel wechselt (Modus 2031, `CSI ? 997 ; 1/2 n`). Die ConPTY von Windows schluckt die Farbabfrage, deshalb starten neue Tabs unter Windows mit der ConPTY aus Windows Terminal, die node-pty mitbringt (*Einstellungen › Terminal › ConPTY aus Windows Terminal*). Die Abfrage beantwortet die App mit dem Hintergrund des Themes (xterm selbst würde den transparenten Hintergrund melden, also Schwarz), und bei einem Wechsel bekommen die Programme, die Modus 2031 eingeschaltet haben, die Meldung. Neue Tabs bekommen außerdem `COLORFGBG`, damit Claude Code auch mit der ConPTY von Windows wenigstens beim Start richtig wählt.
- **node-pty**: Beim Schließen eines Terminals kann in der Konsole „AttachConsole failed“ erscheinen. Das ist bekanntes, harmloses Rauschen von node-pty 1.1.0: Die Prozesse werden trotzdem beendet, in der gepackten App sieht man nichts davon.
